\section{Pipeline}
\label{sec:method_pipeline}

Figure~\ref{fig:pipeline} shows the pipeline. All graphs start from the same source tables. Only the schema in step~3 differs between constructions; every other step is shared.

\begin{enumerate}
    \item \textbf{Data.} The Kaggle F1 tables are restricted to the scope of the study \cite{rao_formula1_kaggle} (Section~\ref{sec:method_data}).

    \item \textbf{Assertions.} The tables are converted once into statements of the form (entity, property, value), such as (a race entry, \texttt{hasTeam}, its team) (Definition~\ref{def:assertions}). Every property used by at least one schema has a source in the tables: either a column or a value derived from several columns, such as \texttt{precedesRace} from season and round. Every non-null value produces one statement. The list defines what information exists, but not how it is written as triples; the schema determines this in steps~3 and~4. Because all graphs are populated from the same list, the data is cleaned and scoped once.

    \item \textbf{Schemas.} Each construction has a schema that defines how each piece of information is written as triples (Section~\ref{sec:method_constructions}).

    \item \textbf{Populating Graph.} Each schema turns the assertions into an RDF graph (Definition~\ref{def:population}).

    \item \textbf{Task preparation.} Information that would reveal the answer is withheld, and the data is split (Section~\ref{sec:method_tasks}). The schemas themselves are not changed. For node classification, the label and race outcomes are removed from the assertions before population, so they do not appear in any graph. For link prediction, the triples of held-out answers are hidden during training and evaluation.

    \item \textbf{Graph tensors and features.} The RDF graph is converted into a typed edge list, and every node receives input features (Section~\ref{sec:method_features}). Features are derived from what the graph states about a node, namely its types or literal value, and never from its name. An instance's features are therefore determined by its set of types. SULO typing changes the input of every instance in addition to adding edges to SULO class nodes.

    \item \textbf{Models.} R-GCN or GraphSAGE computes a representation for every node. For node classification, the final layer outputs one score per race entry. For link prediction, a DistMult decoder scores every candidate (Section~\ref{sec:method_models}).

    \item \textbf{Tuning and evaluation.} Every combination of graph, model, and task is tuned with the same search and evaluated on the same test set (Section~\ref{sec:method_training}).
\end{enumerate}

\section{Data}
\label{sec:method_data}

The data is version~9 of the Kaggle Formula 1 World Championship dataset \cite{rao_formula1_kaggle} and covers every season from 1950 to 2026. Two groups of records are excluded: the Indianapolis 500 (1950--1960), which was run under separate rules with a largely separate field, and shared drives, where one driver has two results for the same race. Missing values are not imputed; a missing value removes only its own assertion.

The resulting scope contains 77 seasons, 1,153 races, 78 circuits, 761 drivers, 182 teams, 27,032 race entries, and 13,782 session results. A \texttt{RaceEntry} corresponds to one row of the race results table. A \texttt{SessionResult} is a qualifying result (from 1994), a sprint result (from 2021), or a practice result (2025--2026). Positions are shared \texttt{Position} entities, one for each observed rank, giving 34 in total. All entries that started third, for example, point to the same \texttt{Position} node.

\section{Knowledge Graphs, Assertions, and Schemas}
\label{sec:method_graphs}

The graphs in this thesis are ordinary RDF knowledge graphs. All three are populated from one shared set of assertions, while the schema determines how each assertion is written as triples. This section defines these terms as they are used in this thesis.

\begin{definition}[Knowledge graph]
\label{def:kg}
A knowledge graph \(G\) is a set of RDF triples \((s, p, o)\) \cite{knowledge_graphs}. The subject \(s\) is an entity, and the object \(o\) is an entity, a class, or a literal. Every subject and object is a node of \(G\). Types are represented by triples \((s, \texttt{rdf:type}, c)\), so classes are nodes as well. Every distinct literal value is also represented by one node shared by all subjects with that value. Every entity has one domain class: \texttt{Season}, \texttt{Race}, \texttt{Circuit}, \texttt{RaceEntry}, \texttt{SessionResult}, \texttt{Driver}, \texttt{Team}, or \texttt{Position}.
\end{definition}

\begin{definition}[Assertions]
\label{def:assertions}
The assertion set \(\mathcal{A}\) is the list of statements \((s, p, v)\) from which every graph is populated: entity \(s\) has value \(v\) for domain property \(p\), where \(v\) is an entity or literal. Examples are (a race entry, \texttt{hasTeam}, its team) and (a race entry, \texttt{hasRacePoints}, \texttt{true}).
\end{definition}

\(\mathcal{A}\) is built once from the database and used by all schemas. It states what information exists, not how it is stored. An assertion always uses the domain property \(p\), even when a graph writes it with different predicates. Pure SULO, for example, writes \texttt{hasRacePoints} using \texttt{sulo:hasFeature} and \texttt{sulo:hasValue}.

\begin{definition}[Schema]
\label{def:schema}
A schema \(S\) decides how assertions are converted to triples. It gives two kinds of rules:
\begin{enumerate}
    \item For every property it covers, one of two \emph{forms}. The \emph{direct} form converts an assertion \((s, p, v)\) into one triple \((s, q, v)\), where \(q\) is the predicate used by the schema for \(p\). The \emph{path} form inserts an intermediate node \(n\) of class \(c\) between \(s\) and \(v\), producing three triples: \((s, q_1, n)\), \((n, \texttt{rdf:type}, c)\), and \((n, q_2, v)\).
    \item For every domain class, optionally, a SULO superclass.
\end{enumerate}
\end{definition}

For example, Ad-hoc writes \texttt{hasRacePoints} in direct form as (entry, \texttt{hasRacePoints}, \texttt{true}). Pure SULO uses the path form: (entry, \texttt{sulo:hasFeature}, \(n\)), (\(n\), \texttt{rdf:type}, \texttt{sulo:Quantity}), (\(n\), \texttt{sulo:hasValue}, \texttt{true}). These two rule types fully determine which triples a schema produces. The schema files were created with the SULO-Compliant Schema Builder \cite{sulo_builder}, and the population code reads the forms directly from them, so no form is written by hand.

\begin{definition}[Population]
\label{def:population}
Populating schema \(S\) with assertions \(\mathcal{A}\) gives graph \(G_S\). Every entity is typed with its domain class and, where defined by \(S\), its SULO superclass. Every assertion is converted using the form assigned to its property. Assertions whose property is not covered by \(S\) are omitted. Each path form creates its own intermediate node, named after its subject and property, such as \texttt{RaceEntry/123/hasRacePoints}.
\end{definition}

Three properties follow from this construction. First, two graphs contain the same assertions for every property covered by both schemas, so differences arise from the schemas. Hybrid and Pure SULO contain the same information, while Ad-hoc does not cover the three properties added by Hybrid or the renamed circuit property (Section~\ref{sec:method_constructions}). Second, intermediate nodes are never shared, while entities are. Two entries that both scored points each receive their own \texttt{sulo:Quantity} node in Pure SULO, whereas two entries that both started third point to the same \texttt{Position} node in every graph. Third, two properties using the same direct predicate can produce the same triple. In Pure SULO, start and finish position are both written as a \texttt{sulo:hasFeature} edge to a \texttt{Position} node, so an entry that started and finished third has one triple for both assertions. In Ad-hoc and Hybrid, the properties use separate predicates and remain distinct.

\section{Graph Constructions}
\label{sec:method_constructions}

The three constructions are different schemas for the same assertion set \(\mathcal{A}\). Each definition below is followed by its schema diagram.

\begin{definition}[Ad-hoc]
\label{def:adhoc}
Ad-hoc is the manually designed F1 domain schema. Each of its 29 properties uses the direct form with the property itself as predicate, and no class has a SULO superclass.
\end{definition}

In Ad-hoc, every assertion becomes one edge, and every instance is typed only with its domain class. Ad-hoc is not a direct mapping of the source tables, where every table would become a class and every column a property \cite{database_to_kg}. A \texttt{RaceEntry} combines information from several tables, positions are shared \texttt{Position} entities rather than column values, and qualifying, sprint, and practice results are represented by one class, \texttt{SessionResult}, distinguished by \texttt{hasSessionType}. Ad-hoc is therefore already a modeled domain graph built with a domain-specific vocabulary.

    \centering
    \includegraphics[width=0.95\textwidth]{Images/adhoc_schema.png}
    \caption{Ad-hoc schema (repeated from Figure~\ref{fig:adhoc_schema}).}
    \label{fig:method_adhoc_schema}
\end{figure}

\begin{definition}[Hybrid]
\label{def:hybrid}
Hybrid extends Ad-hoc with five enrichment units and one renaming:
\begin{enumerate}
    \item \textbf{SULO typing}: every domain class has its SULO superclass (Table~\ref{tab:sulo_classes}), so every instance is typed with both.
    \item \textbf{\texttt{precedesRace}}: a direct \texttt{sulo:precedes} edge from each race to the next race of the same season.
    \item \textbf{\texttt{precedesSeason}}: a direct \texttt{sulo:precedes} edge from each season to the next.
    \item \textbf{\texttt{hasTeamMember}}: a direct \texttt{sulo:hasItem} edge from a team to every driver who drove for it at least once.
    \item \textbf{Rank reification}: \texttt{hasRank} uses the path form through a \texttt{sulo:InformationObject} node (\texttt{sulo:isReferredToIn}, then \texttt{sulo:hasValue}) instead of a direct literal.
\end{enumerate}
In addition, Hybrid renames \texttt{heldAtCircuit} to \texttt{isInCircuit} and writes it as \texttt{sulo:isIn}.
\end{definition}

Units~1--4 add information that can be derived from \(\mathcal{A}\): the SULO type follows from the domain class, \texttt{precedes} from season and round, and team membership from race entries. Unit~5 changes how existing information is stored. The renaming adopts a SULO relation in the same way as units~2--4: \texttt{sulo:isIn} states that the object includes the subject within its extent \cite{dumontier2025sulo}, here a race within its circuit. Unlike the enrichment units, the renaming changes only the predicate of an existing edge. Every race still has exactly one edge to its circuit, and no node or edge is added or removed. It is therefore not treated as an enrichment unit.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.95\textwidth]{Images/hybrid_sulo_schema.png}
    \caption{Hybrid schema (repeated from Figure~\ref{fig:hybrid_schema}).}
    \label{fig:method_hybrid_schema}
\end{figure}

\begin{definition}[Pure SULO]
\label{def:pure}
Pure SULO has the same SULO superclasses and assertions as Hybrid, but writes every property using only SULO predicates (Table~\ref{tab:pure_shapes}).
\end{definition}

Pure SULO uses three kinds of form. Links between entities become one SULO edge. Participation follows the PRO pattern: a race entry is linked to its driver or team through a \texttt{sulo:Role} node. Literal values follow the SOLID pattern: the value is stored on an intermediate information object, quantity, or time node through \texttt{sulo:hasValue} \cite{dumontier2025sulo}. Because SULO has few relations, many Ad-hoc properties share one predicate: \texttt{sulo:hasFeature} writes 15 of them and \texttt{sulo:isReferredToIn} 6. A session result in Pure SULO, for example, has on average 3.2 \texttt{hasFeature} edges in the node classification graph, one of which leads to its position, while in Hybrid the position edge is the only edge of its relation type.

Hybrid and Pure SULO therefore contain the same information but store it differently. Ad-hoc lacks the three derived properties and SULO typing, and stores ranks as direct literals.

\begin{definition}[Enrichment units and ablation variants]
\label{def:ablation}
The ablation variants remove one enrichment unit from Hybrid or add one to Ad-hoc. Each unit corresponds to one schema rule: SULO typing is the set of SULO superclasses, while every other unit is the form of one property. \emph{Hybrid \(-\) \(u\)} is Hybrid with unit \(u\) removed: its rule is taken from Ad-hoc, and a property absent from Ad-hoc (\texttt{precedesRace}, \texttt{precedesSeason}, \texttt{hasTeamMember}) is omitted. \emph{Ad-hoc \(+\) \(u\)} is Ad-hoc with unit \(u\) added, using the rule from Hybrid. The five units in both directions, together with Ad-hoc and Hybrid as controls, produce 12 graphs.
\end{definition}

Removing all five units from Hybrid produces the Ad-hoc graph, except that the circuit predicate keeps its Hybrid name. Adding all five units to Ad-hoc likewise produces Hybrid with the same exception. The five units therefore account for every other difference between the graphs. Their sizes differ: SULO typing adds 43,099 triples, \texttt{hasTeamMember} 1,941, \texttt{precedesRace} 1,076, and \texttt{precedesSeason} 76. Rank reification replaces 34 triples with 102 and adds 34 intermediate nodes.

\section{Distance to Key Information}
\label{sec:method_distance}

RQ\ref{rq:3} asks whether differences between the constructions can be explained by how far the information needed for a prediction lies from its query node. This section defines that distance.

\begin{definition}[Hop distance]
\label{def:hops}
The distance between two nodes is the number of edges on their shortest path, ignoring edge direction. The \(K\)-hop neighborhood of a node contains every node within distance \(K\).
\end{definition}

A message-passing network with \(K\) layers computes a node's output from input features within its \(K\)-hop neighborhood \cite{gilmer2017mpnn}. Every triple is used in both directions (Section~\ref{sec:method_features}), so edge direction does not limit this neighborhood. If a construction places relevant information further away, a model of the same depth may no longer reach it.

\begin{definition}[Key information]
\label{def:key_information}
The \emph{key information} of a task is the set of literal values that most strongly indicate its answer, chosen from domain knowledge. Its distance \(h_S\) in schema \(S\) is the number of hops from the query node to these literals.
\end{definition}

The key information is defined in terms of literals because entities are distinguished only through their literals. An entity's input features encode only its types (Section~\ref{sec:method_features}), so two drivers, for example, appear identical to the model until their names, birth dates, or nationalities are within reach. The key information is an indicator of the answer, not the answer itself. For each task it is defined as follows (Table~\ref{tab:key_information}):

\begin{itemize}
    \item \textbf{NC}: the entry's own grid rank. The grid is the order in which cars line up at the start, set mostly by qualifying; rank~1 starts at the front. Ranking entries by grid position alone gives a ROC-AUC of 0.835.
    \item \textbf{LP team}: the literals of the entry's driver, which identify the driver and thereby the team that driver raced for in that season.
    \item \textbf{LP position}: the rank of one of the entry's session results, such as its qualifying position, which largely determines the grid slot.
    \item \textbf{LP circuit}: the literals of the race, such as its name, which identifies the circuit for most races.
\end{itemize}

The grid-only rule and one-rule baselines (Section~\ref{sec:method_training}) use the same information and show how strongly each indicator predicts the answer.

The distance \(h_S\) follows from the schema alone. The key information is reached from the query node through a chain of properties (Table~\ref{tab:key_information}). Each direct property adds one hop, while each path form adds two because of its intermediate node; the \texttt{rdf:type} edge of that node is not part of the chain. Because \(h_S\) is known before training, it gives the smallest depth at which the key information becomes reachable for each construction and task. Experiment E3 uses these depths as its predictions (Section~\ref{sec:design_e3}).

\section{Prediction Tasks}
\label{sec:method_tasks}

\subsection{Node Classification}

\begin{definition}[Node classification]
\label{def:nc}
Node classification predicts, for each of the 27,032 \texttt{RaceEntry} entities, whether it scored championship points. The label is 1 when its points value is greater than 0 and 0 otherwise. The input graph is populated from assertions without the label (\texttt{hasRacePoints}) and race outcomes (\texttt{hasFinishPosition}, \texttt{hasStatus}, \texttt{hasLapsCompleted}).
\end{definition}

The label is positive for 31.3\% of entries. The three race outcomes are removed with the label because they are only known after the race and would reveal it: finishing position alone predicts the label with a ROC-AUC of 0.985. Information known before the race, including grid position and qualifying, sprint, and practice results, remains. The label and outcomes are removed for every entry, so no race outcome is visible to the model. Because removal happens before population, a path form is removed together with its intermediate node.

Entries are split 80/10/10 into training, validation, and test sets, stratified by label (21,625 / 2,703 / 2,704 entries). The same split is used for every graph and both models. A temporal split is not used because the share of positive labels changes across eras, while sprint and practice data exist only in recent seasons. A temporal split would therefore mix the effect of time with the effect of graph construction.

\subsection{Link Prediction}

\begin{definition}[Link prediction query]
\label{def:lp}
A query \((h, r, ?)\) asks for the answer \(t^*\) of target \(r\) for head entity \(h\). The model ranks every candidate in \(C_r\), the set of all entities of the answer class. The three targets are
\begin{center}
\begin{tabular}{llll}
    \toprule
    Target \(r\) & Head class & Property & Candidates \(C_r\) \\
    \midrule
    \emph{team} & \texttt{RaceEntry} & \texttt{hasTeam} & 182 \texttt{Team} entities \\
    \emph{position} & \texttt{RaceEntry} & \texttt{hasStartPosition} & 34 \texttt{Position} entities \\
    \emph{circuit} & \texttt{Race} & \texttt{heldAtCircuit} & 78 \texttt{Circuit} entities \\
    \bottomrule
\end{tabular}
\end{center}
Every head has exactly one answer.
\end{definition}

A target is an Ad-hoc property of the assertions (Definition~\ref{def:assertions}), not a graph predicate. A query asks for the object of one assertion, such as the team in \texttt{hasTeam}(\(e\), \(t\)), and its answer is read from the assertions. The question is therefore identical across graphs, regardless of how that property is represented. Using predicates directly would not provide this equivalence: in Pure SULO, team and driver use the same role path, while start and finish position both use \texttt{sulo:hasFeature}. Knowledge graph completion usually reports filtered ranks, where other correct answers to a query are removed before ranking. Every head here has exactly one answer, so raw and filtered ranks are identical.

The three targets are selected from the nine Ad-hoc properties that link two entities: \texttt{hasDriver}, \texttt{hasTeam}, \texttt{hasStartPosition}, \texttt{hasFinishPosition}, \texttt{hasPosition}, \texttt{hasRaceEntry}, \texttt{hasSessionResult}, \texttt{heldAtCircuit}, and \texttt{partOfSeason}. All three graphs contain these properties in their own form. The remaining properties link entities to literals or are enrichments absent from Ad-hoc, so they cannot be targets in all three graphs.

Of the nine entity links, \texttt{hasRaceEntry} and \texttt{hasSessionResult} are excluded because every answer belongs to one head only, so no answer is observed during training. \texttt{partOfSeason} follows directly from the year of the race date. \texttt{hasFinishPosition} is a race outcome and restates the NC label. \texttt{hasPosition}, the session position, is close to the grid slot and exists only from 1994. \texttt{hasDriver} would have to be hidden together with team because both use the same role path in Pure SULO.

The targets are chosen to test the graph constructions, not for their value as F1 predictions. The team of every entry and circuit of every race are already recorded in the data, and a single rule recovers most of them (Section~\ref{sec:method_training}, paragraph \emph{Baselines}). As in the knowledge graph completion benchmarks FB15k-237 and WN18RR \cite{toutanova2015observed,dettmers2018conve}, known information is hidden and the model must recover it from the rest of the graph. A target therefore measures whether a construction keeps the key information for an assertion within reach.

Each target depends on a different part of the schema where the constructions differ (Table~\ref{tab:key_information}):

\begin{itemize}
    \item \emph{team} is a participation. Pure SULO represents it through a role node (the PRO pattern), so the team lies two hops from the entry instead of one. Hybrid and Pure SULO also link each team to its drivers with \texttt{hasTeamMember}, creating a second route from an entry to its team: from the entry to its driver, and from the driver to the teams that driver raced for.
    \item \emph{position} links an entry to a shared \texttt{Position} hub whose rank is reified in Hybrid and Pure SULO.
    \item \emph{circuit} is the only target whose head is a race. The race's literals are one hop away in Ad-hoc and Hybrid and two in Pure SULO.
\end{itemize}

The link prediction graph keeps every assertion except \texttt{hasFinishPosition}, which is removed for every entry because in Pure SULO it can become the same triple as start position (Section~\ref{sec:method_graphs}). Points, status, and completed laps remain.

In node classification, labels are never part of the graph. In link prediction, the answers normally are: each target assertion appears as either a triple or a path. If an evaluated answer remains visible, the model can read it directly from its own edge, which does not test whether the rest of the graph identifies it. The answers to evaluated queries are therefore removed, as are the answers to training queries supervised in that epoch.

Answers are hidden by race rather than by individual query. A \emph{team} or \emph{position} query belongs to the race of its entry, while a \emph{circuit} query belongs directly to its race. Answers within the same race depend on one another: grid positions form a permutation, so visible positions narrow down a hidden one, while a teammate's visible team can reveal another entry's team.

The races are split 80/10/10 (922 / 115 / 116 races), with the same split used for every graph and both models. This gives 21,658 / 2,639 / 2,735 \emph{team} queries, 20,321 / 2,504 / 2,575 \emph{position} queries, and 922 / 115 / 116 \emph{circuit} queries.

\begin{definition}[Hidden race]
\label{def:hidden}
Hiding a set of races \(H\) removes two kinds of triples from the graph:
\begin{enumerate}
    \item the triples of every target assertion belonging to a race in \(H\): the \texttt{hasTeam} and \texttt{hasStartPosition} assertions of its entries and the race's \texttt{heldAtCircuit} assertion, including all triples of a path form;
    \item every \texttt{hasTeamMember} triple from team \(t\) to driver \(d\) for which all entries in which \(d\) drove for \(t\) belong to races in \(H\).
\end{enumerate}
\end{definition}

Condition~2 is needed because \texttt{hasTeamMember} creates a second route to the team (see the \emph{team} target above). If driver \(d\) drove for team \(t\) only in hidden races, the triple \(t\) \texttt{hasTeamMember} \(d\) would still reveal that relationship. If \(d\) also drove for \(t\) in a visible race, the membership remains because it is supported by a visible assertion. A check on every graph confirms that no hidden assertion can be reached directly, through a role node, or through a membership without a visible supporting entry.

The set of hidden races \(H\) depends on the stage:

\begin{itemize}
    \item \textbf{Training}: in each epoch, \(H\) contains the validation and test races and a random 30\% of the training races. The loss uses the queries from that 30\%.
    \item \textbf{Validation}: \(H\) contains the validation and test races, and the validation queries are scored.
    \item \textbf{Test}: after retraining on the training and validation races, \(H\) contains the test races, and the test queries are scored.
\end{itemize}

Hiding supervised queries during training is common in GNN link prediction and is not needed for node classification. If training answers remained visible, the model could learn to copy the answer edge, a shortcut unavailable for hidden validation and test queries. PyTorch Geometric implements this using a disjoint set of supervision edges and uses a ratio of 30\% in its link prediction tutorial \cite{fey2019fastgraphrepresentationlearning}, which is also used here. R-GCN's link prediction model similarly drops a share of edges during each training step \cite{rgcn_cite}.

\section{Graph Tensors and Node Features}
\label{sec:method_features}

Each triple \((s, p, o)\) becomes two directed edges: \(s \to o\) with relation type \(p\), and \(o \to s\) with its own inverse relation type. This follows R-GCN, which uses every relation in both directions \cite{rgcn_cite}. The \texttt{rdf:type} triples are retained because typing is part of each construction.

Node features never use IRI text. Each node is described by a key and, for some literals, a value:

\begin{itemize}
    \item an instance by its set of \texttt{rdf:type} classes;
    \item a class by the class itself;
    \item a numeric or date literal by its datatype, with its value standardized across all literal nodes of that datatype (dates as fractional years);
    \item a boolean literal by its datatype, with value 0 or 1;
    \item a string literal by the string itself.
\end{itemize}

For every key \(k\), the model learns two 256-dimensional vectors: a base vector \(a_k\) and a value vector \(b_k\). A node with key \(k\) and value \(x\) starts from \(a_k + x\,b_k\), while a node without a value, meaning an instance, class, or string, starts from \(a_k\) alone. Literals of the same numeric datatype therefore lie on a learned line ordered by value.

One additional input is appended to every node: its degree in the graph visible to the model, represented as standardized \(\log(1 + \text{degree})\). Each node therefore has 257 input features.

Two entities with the same set of types start with the same features and differ only through their neighbors. SULO typing changes the key of every instance. A common alternative is to give every node its own learned embedding, as in the original R-GCN \cite{rgcn_cite}. In that case, the input would not depend on types, and SULO typing would reach the model only through edges to class nodes. Every distinct literal remains one node shared by all subjects with that value, as in the RDF graph itself.

%-------------------------------------------------------------------------
\section{Models}
\label{sec:method_models}

Both encoders have \(K\) message-passing layers of width \(d\), with ReLU and dropout between layers and \(h^{(0)}_v = x_v\). The dropout rates follow the PyTorch Geometric reference examples: 0.2 for R-GCN and 0.5 for GraphSAGE.

\paragraph{R-GCN.}
Each layer computes \cite{rgcn_cite}
\[
h^{(l+1)}_v = W^{(l)}_0 h^{(l)}_v + \sum_{r=1}^{R} \frac{1}{|N_r(v)|} \sum_{u \in N_r(v)} W^{(l)}_r h^{(l)}_u + b^{(l)},
\qquad
W^{(l)}_r = \sum_{j=1}^{B} c^{(l)}_{rj} V^{(l)}_j,
\]
where
\begin{itemize}
    \item \(h^{(l)}_v\) is the representation of node \(v\) after layer \(l\), with \(h^{(0)}_v = x_v\) its input features (Section~\ref{sec:method_features});
    \item \(R\) is the number of relation types, including inverses (Table~\ref{tab:graph_sizes});
    \item \(N_r(v)\) is the set of neighbors of \(v\) under relation type \(r\);
    \item \(W^{(l)}_r\) is the weight matrix for relation type \(r\), \(W^{(l)}_0\) the matrix applied to the node itself, and \(b^{(l)}\) a bias;
    \item \(V^{(l)}_1, \ldots, V^{(l)}_B\) are \(B\) basis matrices shared across relation types, and \(c^{(l)}_{rj}\) is the learned coefficient of basis \(j\) for relation \(r\).
\end{itemize}

With basis decomposition, each relation matrix is a combination of the \(B\) shared bases, reducing the number of parameters when \(R\) is large. Without it, every relation type has its own free matrix.

\paragraph{GraphSAGE.}
Each layer uses the mean aggregator \cite{graphsage_cite}:
\[
h^{(l+1)}_v = W^{(l)}_1 h^{(l)}_v + W^{(l)}_2 \frac{1}{|N(v)|} \sum_{u \in N(v)} h^{(l)}_u + b^{(l)},
\]
where
\begin{itemize}
    \item \(h^{(l)}_v\) is the representation of node \(v\) after layer \(l\), as for R-GCN;
    \item \(N(v)\) is the set of all neighbors of \(v\), regardless of relation type;
    \item \(W^{(l)}_1\) is the weight matrix applied to the node itself, \(W^{(l)}_2\) the matrix applied to the mean of its neighbors, and \(b^{(l)}\) a bias.
\end{itemize}

Unlike R-GCN, GraphSAGE uses one weight matrix for all neighbors and therefore does not distinguish relation types. Applying one linear map to the concatenation of \(h_v\) and the neighbor mean, as in the original formulation, is equivalent to this sum. Neighbors are averaged directly, without a learned layer before the mean. The aggregator is fixed in advance and is not tuned.

\paragraph{Node classification head.}
The final layer has one output: the logit \(s_e\) of entry \(e\). The loss is binary cross-entropy between \(\sigma(s_e)\) and \(y(e)\), averaged over the training entries.

\paragraph{Link prediction head.}
The final layer outputs an embedding \(e_v \in \mathbb{R}^{d}\). A DistMult decoder scores each candidate as
\[
\phi(h, r, t) = \sum_{i=1}^{d} e_{h,i}\, w_{r,i}\, e_{t,i},
\]
where
\begin{itemize}
    \item \(e_h\) and \(e_t\) are the output embeddings of head \(h\) and candidate \(t\), and \(e_{h,i}\) is the \(i\)-th entry of \(e_h\);
    \item \(w_r \in \mathbb{R}^{d}\) is a learned vector, one for each target \(r\);
    \item \(d\) is the embedding size.
\end{itemize}

This is the decoder used by the R-GCN link prediction model \cite{yang2015embeddingentitiesrelationslearning,rgcn_cite}. The loss is cross-entropy over all candidates for a query \cite{dettmers2018conve,ruffinelli2020olddog}:
\[
\mathcal{L} = -\frac{1}{|Q_B|} \sum_{(h, r, t^*) \in Q_B} \log \frac{\exp \phi(h, r, t^*)}{\sum_{t \in C_r} \exp \phi(h, r, t)},
\]
where
\begin{itemize}
    \item \(Q_B\) is the set of queries from the training races supervised in that epoch (Section~\ref{sec:method_tasks});
    \item \(t^*\) is the answer to query \((h, r, ?)\), and \(C_r\) is the candidate set for target \(r\).
\end{itemize}

The loss is therefore the negative log-probability of the correct answer under a softmax over all candidates. Every query has equal weight. One model is trained per graph and encoder for all three targets together.

%-------------------------------------------------------------------------
\section{Training, Tuning, and Evaluation}
\label{sec:method_training}

\paragraph{Training.}
Training is full-batch: each epoch consists of one forward pass over the complete graph and one Adam step \cite{kingma2015adam}. Training runs for at most 400 epochs, the largest value in GraphGym's design space \cite{you2020graphgym}. Early stopping uses validation ROC-AUC for NC or validation MRR pooled across all targets for LP, with a patience of 50 epochs, and restores the best weights. The first 50 epochs are treated as warm-up: they are trained but neither checkpointed nor counted toward the patience, because otherwise unstable validation scores from the first epochs could be retained as the best result.

\paragraph{Metrics.}
For NC, the main metric is ROC-AUC; PR-AUC is also reported, and accuracy and F1 use a fixed threshold of 0.5.

For LP, the answer's rank is its position among all candidates in \(C_r\), ordered by score. It is one plus the number of candidates scoring higher than the answer, plus half the number of other candidates with the same score. Ties therefore receive the average of their best and worst possible rank. A model cannot benefit from assigning every candidate the same score: doing so gives the middle rank rather than rank~1. MRR is the mean of \(1/\mathrm{rank}\), while Hits@\(k\) is the share of queries with \(\mathrm{rank} \le k\), for \(k \in \{1, 3, 10\}\). Both are reported per target and pooled across all queries.

\paragraph{Hyperparameter search.}
Each combination of graph, encoder, and task is tuned separately with the same search, giving 12 searches. Table~\ref{tab:search_space} gives the search space. The search has four phases:

\begin{enumerate}
    \item a joint grid over width and depth, using the default learning rate, weight decay, and number of bases;
    \item at the phase-1 winner, the number of bases (R-GCN only), followed by learning rate and then weight decay, with earlier choices fixed;
    \item a \(2 \times 2\) verification grid using the two best widths at the winning depth and the two best combinations of bases, learning rate, and weight decay from phase~2;
    \item the winner is retrained on the training and validation data for its median best epoch plus one, without early stopping, and evaluated once on the test set for each final seed.
\end{enumerate}

In phases~1--3, every configuration is trained with seeds \(\{0, 1, 2\}\) and ranked by its mean validation metric. Phase~4 uses seeds \(\{0, \ldots, 4\}\), with results reported as mean \(\pm\) standard deviation across these seeds.

\paragraph{Checks.}
Each model is also trained once with shuffled labels for NC or shuffled answers for LP, which must produce a chance-level test score. This checks that the pipeline does not leak labels or answers.

\paragraph{Baselines.}
The baselines involve no training. For NC, a grid-only rule ranks every entry by its starting grid slot, with entries missing a grid position ranked last. It measures how much the single most informative pre-race assertion predicts the label. A hub-degree rule ranks every entry by the degree of its starting \texttt{Position} node instead, which is the degree every model receives as an input (Section~\ref{sec:method_features}). That node is one hop from its entries in all three graphs, so the rule measures how much grid information a model can obtain without reaching the rank literal. Both rules give the same ranking in every graph, because typing and the rank representation add the same number of edges to every \texttt{Position} node.

For LP, the frequency baseline ranks candidates by how often they answer the target in the races the model may learn from: the training races when the validation set is scored, and the training and validation races when the test set is scored. This is the best score available when the graph provides no information about a query. The one-rule baselines predict the driver's most frequent team in the same season, the most frequent circuit for the race name, and the qualifying position, falling back to the driver's most frequent grid slot in that season. The grid-only and one-rule baselines are reference points rather than targets for the models: they identify information that indicates the answer, which the models must learn from the graph.

\paragraph{Implementation.}
The pipeline is implemented in Python with PyTorch Geometric \cite{fey2019fastgraphrepresentationlearning} and runs on one 12~GB GPU. R-GCN layers use gradient checkpointing so that full-batch training fits in memory. This changes memory use but not the outputs.
